# Техническое задание: Converter 2.0

Версия документа: 0.6 · Дата: 2026-10-22 · Этапы 1–2 реализованы, этап 3 — на Linux, см. раздел 15

## 1. Общие сведения

**Назначение.** Десктоп-приложение для пакетной конвертации фото и видео (в первую очередь с iPhone: HEIC, HEVC/MOV) в распространённые форматы и для поиска и удаления дубликатов файлов. Всё работает в одном окне.

**Платформы:**
- Windows 10 (22H2) / 11 x64;
- Linux x64 (Ubuntu 22.04+, Arch-подобные, в т.ч. CachyOS), Wayland и X11.

**Стек:**
- Ядро на **Rust** (workspace из `core`, `cli`, `app`).
- GUI на **Tauri 2** + **React + TypeScript** (Vite).
- Видео: внешний процесс **ffmpeg/ffprobe** (sidecar), которым управляет ядро.
- Фото: **libheif** (через `libheif-rs`) для HEIC/HEIF/AVIF, Rust-кодировщики для PNG/JPEG/WebP.

**Замещает** прежний Python-скрипт (`main.py`, `converters.py`, `ffmpeg_utils.py`, `config.py`). Он удалён из проекта 2026-10-21, после этапа 1.

**Лицензия приложения:** MIT.

## 2. Термины

| Термин | Значение |
|---|---|
| Задача | Обработка одного файла: конвертация или хэширование |
| Очередь | Список задач текущего запуска |
| Перепаковка (remux) | Перенос потоков в другой контейнер без перекодирования (`-c copy`) |
| HW-кодировщик | Аппаратный кодек видеокарты: NVENC (NVIDIA), QSV (Intel), AMF (AMD), VAAPI (Linux) |
| Бюджет потоков | Число логических ядер CPU, которое приложению разрешено занять в данный момент |
| Уровень нагрузки | Пользовательская настройка, из которой вычисляется бюджет потоков (раздел 6) |
| Группа дубликатов | Набор файлов, признанных одинаковыми |
| Live Photo | Пара файлов iPhone с общим именем: фото (HEIC/JPEG) и короткое видео (MOV) |
| HDR-видео | Видео с передаточной характеристикой HLG или PQ, обычно 10 бит; на iPhone — Dolby Vision 8.4 с базовым слоем HLG |

## 3. Сценарии использования

**Главный пользователь** — пожилой человек без опыта работы с компьютером, которому нужно перенести фото и видео с телефона и освободить место. Интерфейс проектируется под него (раздел 8.5); опытному пользователю остаются «Расширенные настройки» и CLI.


1. Пользователь перетаскивает в окно папку с телефона. Приложение показывает 300 фото и 40 видео. Пользователь выбирает «Фото → JPEG», «Видео → Совместимо (H.264)», нажимает «Старт» и продолжает работать за компьютером: уровень «Авто» не мешает остальным программам.
2. Пользователь запускает поиск дубликатов по двум папкам. Приложение показывает группы с превью и само отмечает лишние файлы (оставляя самый старый). Пользователь проверяет выбор и отправляет лишнее в корзину.
3. После конвертации с сохранением исходников пользователь в один клик ищет дубликаты в папке результата. Приложение находит точные копии и пары «одно и то же фото в разных форматах» (HEIC + JPEG). Для пар предлагается оставить файл выбранного формата.
4. Опытный пользователь запускает то же самое из терминала через CLI с теми же параметрами.

## 4. Функциональные требования: конвертация

### 4.1 Добавление файлов

- **FR-1.1.** Файлы и папки добавляются:
  - перетаскиванием в окно;
  - кнопками «Добавить файлы» и «Добавить папку»;
  - через аргументы командной строки при запуске.

  Если приложение уже открыто, повторный запуск с файлами передаёт их в открытое окно (одиночный экземпляр).
- **FR-1.2.** Обход папок:
  - рекурсивный (переключатель, по умолчанию включён);
  - скрытые и системные файлы пропускаются (настраивается);
  - символические ссылки и junction-точки не раскрываются.
- **FR-1.3.** Тип файла определяется **по содержимому**, а не только по расширению. Пример: `Я-люблю-свою-работу-финал.HEVC` на деле является контейнером с потоками HEVC и AAC.
  - Фото определяются по сигнатуре: это быстро.
  - Видео дополнительно проверяются ffprobe. Пробы выполняются параллельно и не блокируют интерфейс.
- **FR-1.4.** Колонки списка:
  - миниатюра, имя, тип, размер;
  - разрешение / длительность / кодек, метка HDR;
  - выбранный выходной формат;
  - статус с прогрессом.
- **FR-1.5.** Список виртуализирован и не тормозит при 100 000 строк. Есть фильтр по типу и поиск по имени.
- **FR-1.6.** Из списка можно убрать выбранные файлы или очистить его целиком. Повторно добавленный файл (совпадение канонического пути) в очередь не дублируется.
- **FR-1.7. Live Photo.** Приложение распознаёт пары (одинаковое имя, фото + MOV до 4 с в той же папке). Опция «Пропускать видео Live Photo» включена по умолчанию.
- **FR-1.8.** Из многокадровых HEIC (серии, «Портрет» с картой глубины) конвертируется только основное изображение.

### 4.2 Входные и выходные форматы

| Категория | Вход | Выход |
|---|---|---|
| Фото | HEIC/HEIF, AVIF, JPEG, PNG, WebP, BMP, TIFF | PNG, JPEG, WebP |
| Видео | MOV, MP4, M4V, MKV, AVI, WebM, 3GP; кодеки HEVC, H.264, VP9, AV1, ProRes, MPEG-4 | MP4 (H.264), MP4 (HEVC), MKV, WebM (AV1 / VP9) |
| Аудио из видео | любой из видео-входов | MP3, M4A (AAC) |

- Если выходной формат совпадает с входным и никакие параметры не меняются (размер, качество, метаданные), файл пропускается со статусом «Уже в нужном формате».
- RAW (DNG, ProRAW) и выход AVIF — вне рамок v1 (раздел 13).

### 4.3 Параметры конвертации: фото

- **FR-2.1. Параметры:**
  - формат;
  - качество (JPEG/WebP: 1–100, по умолчанию 90);
  - сжатие PNG: «Быстро» (по умолчанию) / «Компактно»;
  - уменьшение по большей стороне (выключено / N px).
- **FR-2.2. Метаданные.**
  - EXIF, XMP и ICC-профиль по умолчанию переносятся в результат.
  - Можно удалить GPS-координаты.
  - Можно удалить все метаданные целиком.
- **FR-2.3. Ориентация.**
  - Поворот и отражение применяются к пикселям. В результате тег EXIF Orientation равен 1, чтобы картинку не повернуло второй раз.
  - Для HEIC/AVIF источником истины являются преобразования контейнера (`irot`, `imir`, `clap`), а не тег EXIF.
- **FR-2.4. Цвет.**
  - Фото iPhone в профиле Display P3 сохраняются с этим профилем (по умолчанию).
  - Опция «Преобразовать в sRGB» нужна для программ, которые игнорируют профиль.
  - Без профиля цвета на результате станут тусклее или ярче — это недопустимо.
- **FR-2.5. Глубина цвета.**
  - 10-битные HEIC сохраняются в 8 бит.
  - Для PNG доступна опция «16 бит».
  - HDR gain map в v1 не переносится, используется базовое SDR-изображение.
- **FR-2.6. Ограничения форматов.** WebP поддерживает не более 16 383 px по стороне. Если изображение больше, предлагается уменьшить его до предела; без согласия файл получает ошибку «Слишком большое для WebP».

### 4.4 Параметры конвертации: видео

- **FR-3.1. Режим видео:**

| Режим | Целевые кодеки | Поведение |
|---|---|---|
| **Совместимо** (по умолчанию) | H.264 8 бит + AAC, MP4 | Если источник уже H.264 8 бит + AAC/MP3 — перепаковка. Иначе перекодирование видео; аудио копируется, если совместимо |
| **Компактно** | HEVC + AAC, MP4, тег `hvc1` | Если источник уже HEVC — перепаковка. В интерфейсе предупреждение: на Windows для просмотра нужно расширение HEVC |
| **WebM** | AV1 (по умолчанию) или VP9 + Opus | AV1: аппаратно при наличии, иначе SVT-AV1. VP9: только CPU, медленно, с предупреждением |
| **MKV** | копирование всех потоков | Перекодирование только если пользователь сам задал кодек |
| **Ручной** | кодек, CRF/QP, пресет, битрейт аудио, разрешение, FPS | |

- **FR-3.2. Профили качества:** «Быстро», «Сбалансированно» (по умолчанию), «Высокое качество». Для каждого кодировщика профиль переводится в его собственные параметры (CRF у x264/x265/SVT-AV1, QP у VAAPI, global_quality у QSV, cq у NVENC, qp_i/qp_p у AMF). Таблица соответствий хранится в ядре и покрыта тестами.
- **FR-3.3. HDR.** Если источник HDR, а цель 8-битная (режим «Совместимо»), выполняется тональная компрессия в SDR BT.709:
  - на GPU: `tonemap_vaapi`, `vpp_qsv`, `libplacebo`;
  - иначе на CPU: `zscale` + `tonemap`.

  Без этого видео iPhone выглядит блёклым. В режиме «Компактно» HDR сохраняется как HEVC Main10, если кодировщик это умеет; иначе тоже тональная компрессия.
- **FR-3.4. Сохранение свойств исходника:**
  - **поворот:** `displaymatrix` сохраняется при перепаковке и применяется к кадрам при перекодировании;
  - **частота кадров:** переменная частота сохраняется (`-fps_mode passthrough`);
  - **метаданные:** дата съёмки и геопозиция переносятся (`-map_metadata 0`, `-movflags use_metadata_tags`); опция удаления GPS общая с фото;
  - `-movflags +faststart` для MP4.
- **FR-3.5. Выбор потоков:**
  - берётся первый видеопоток;
  - берётся первая **декодируемая** аудиодорожка: неподдерживаемые кодеки (например, Apple APAC) пропускаются с предупреждением в журнале;
  - служебные дорожки iPhone (`mebx`, таймкод) в MP4 не переносятся — иначе перепаковка падает.
- **FR-3.6. Аудио:**
  - копируется, если кодек допустим в целевом контейнере;
  - иначе перекодируется: в AAC 192 кбит/с, а для WebM — в Opus 128 кбит/с.
- **FR-3.7. Аппаратное ускорение.** Варианты: «Авто» (по умолчанию), выбор конкретного кодировщика или «Выключено».
  - При первом запуске, при смене версии ffmpeg или драйвера делается пробное кодирование 10 кадров каждым кандидатом и каждым кодеком (H.264, HEVC, HEVC 10 бит, AV1). Результат кэшируется.
  - Порядок кандидатов: Windows — NVENC → QSV → AMF; Linux — VAAPI → NVENC → QSV.
  - При нескольких GPU выбирается дискретный. Устройство можно задать вручную (Linux: `/dev/dri/renderD*`; Windows: адаптер D3D11).
  - Декодирование тоже идёт на видеокарте, если она поддерживает исходный кодек и профиль. Иначе декодирует CPU, а кодирует GPU.
  - Если ничего не работает, используется программный кодировщик (libx264 / libx265 / SVT-AV1).
- **FR-3.8.** Если HW-кодирование файла падает с ошибкой, файл автоматически перекодируется на CPU. Это отражается в журнале.

### 4.5 Вывод

- **FR-4.1. Папка результата:**
  - «Рядом с исходным» (по умолчанию);
  - «В выбранную папку»;
  - «В выбранную папку с сохранением структуры подпапок».
- **FR-4.2. Шаблон имени,** по умолчанию `{name}`. Доступны переменные:
  - `{name}`, `{ext}`, `{n}`;
  - `{date}` — дата съёмки: EXIF `DateTimeOriginal` или QuickTime `creationdate`/`creation_time`; если их нет — mtime.

  Недопустимые для ФС символы и зарезервированные имена Windows (`CON`, `NUL`…) заменяются на `_`.
- **FR-4.3. Конфликт имён:** добавить суффикс `_1`, `_2`… (по умолчанию) / перезаписать / пропустить.
  - Имена резервируются **на этапе планирования**, до запуска задач. Так два параллельных файла (`IMG_1.HEIC` и `IMG_1.PNG` → `IMG_1.jpg`) не получат одно имя.
  - Результат никогда не записывается поверх собственного исходника.
- **FR-4.4. Атомарная запись.**
  - Результат пишется во временный файл в целевой папке с именем `.<имя>.cvtmp-<id>.<ext>`. Расширение нужно, чтобы ffmpeg определил формат.
  - После проверки (FR-5.2) временный файл переименовывается в финальное имя.
  - Пути всех временных файлов записываются в журнал незавершённых операций. При старте приложения удаляются **только** файлы из этого журнала: чужие файлы с похожими именами не трогаются.
- **FR-4.5.** Дата изменения результата копируется с исходника (опция, по умолчанию включено).
- **FR-4.6. Место на диске.**
  - Перед стартом выводится оценка размера результата. Если места мало, приходит предупреждение.
  - Если место кончилось во время работы, очередь ставится на паузу, а не валит все оставшиеся файлы ошибками.

### 4.6 Исходные файлы после конвертации

- **FR-5.1.** Варианты: «Оставить» (по умолчанию) / «В корзину» / «Удалить навсегда». Для последнего нужно отдельное подтверждение.
- **FR-5.2.** Исходник удаляется **только после успешной проверки результата**:
  - файл существует и не пуст;
  - ffprobe его открывает;
  - длительность видео отличается от исходной не более чем на 0.5 с или 1 %;
  - фото декодируется, размер в пикселях совпадает с ожидаемым.
- **FR-5.3.** При ошибке или отмене исходник **никогда** не удаляется. Текущий `main.py` удаляет исходник в `finally` даже при ошибке — это поведение не переносится.
- **FR-5.4.** Если корзина недоступна (сетевой диск, съёмный носитель без корзины), приложение **спрашивает**, что делать: оставить или удалить навсегда. Молча удалять навсегда нельзя.
- **FR-5.5.** У Live Photo, у которой видео пропущено (FR-1.7), исходный MOV удаляется вместе с фото только при отдельно включённой опции.

### 4.7 Выполнение и прогресс

- **FR-6.1.** Прогресс отдельно по каждому файлу (процент, скорость `×realtime` или МБ/с, оставшееся время) и общий (файлы, байты, оставшееся время).
- **FR-6.2.** Кнопки:
  - «Пауза» — новые задачи не запускаются, запущенные доделываются;
  - «Отмена всего»;
  - отмена одного файла из контекстного меню.
- **FR-6.3. Отмена и аварийное завершение.**
  - Отмена занимает не более 2 с: дерево процессов ffmpeg завершается, временные файлы удаляются.
  - Дочерние процессы привязаны к приложению: Job Object на Windows, `PR_SET_PDEATHSIG` и группа процессов на Linux. Если приложение упадёт, ffmpeg не останется висеть.
- **FR-6.4.** Ошибка одного файла не останавливает очередь. В конце показывается сводка «успешно / пропущено / ошибки» с кнопкой «Повторить ошибочные».
- **FR-6.5.** Журнал (вкладка «Журнал»): подробности по каждой задаче, включая команду ffmpeg и stderr при ошибке. Журнал можно экспортировать в файл.
- **FR-6.6.** По завершении приходит системное уведомление, если окно не в фокусе.
- **FR-6.7.** Пока идёт обработка, система не уходит в сон:
  - Windows: `SetThreadExecutionState`;
  - Linux: inhibit через `org.freedesktop.login1`.

  Отключается в настройках.
- **FR-6.8.** Закрытие окна во время работы требует подтверждения: «Отменить и выйти» / «Продолжить».

## 5. Функциональные требования: дубликаты

### 5.1 Область поиска

- **FR-7.1.** Одна или несколько папок, обход рекурсивный.
  - Если одна выбранная папка вложена в другую, файлы не считаются дважды: пути канонизируются.
  - Символические ссылки не раскрываются.
- **FR-7.2. Фильтры:**
  - типы (все / фото / видео / свой список расширений);
  - минимальный размер (по умолчанию 1 КБ);
  - исключаемые папки и маски.
- **FR-7.3.** Жёсткие ссылки на один и тот же файл (одинаковые inode / file ID) дубликатами не считаются и помечаются отдельно. Если такой файл одновременно совпадает по содержимому с другим файлом, в группе он показывается один раз с пометкой «+N ссылок». При удалении удаляются все его имена: иначе место не освободится.
- **FR-7.4.** Облачные файлы, которых нет на диске (OneDrive Files On-Demand и аналоги, атрибут `RECALL_ON_DATA_ACCESS`), по умолчанию пропускаются. Иначе хэширование скачает всё облако. Опция «Включить облачные файлы» идёт с предупреждением.

### 5.2 Точные дубликаты (по содержимому)

- **FR-8.1.** Поиск идёт в три шага; к следующему шагу проходят только совпавшие на предыдущем:
  1. группировка по размеру;
  2. хэш первых и последних 64 КБ;
  3. полный хэш **BLAKE3**.
- **FR-8.2.** Кэш хэшей хранится на диске (каталог кэша, раздел 7). Ключ записи: путь + размер + mtime + inode / file ID. Повторный поиск по неизменённой папке из 100 000 файлов занимает не более 5 с.

### 5.3 Похожие фото и одинаковые фото в разных форматах

- **FR-9.1.** Перцептивный хэш (`image_hasher`, pHash) по уменьшенной копии с применённой ориентацией. Порог похожести задаётся ползунком «Строго ↔ Мягко». Для HEIC используется встроенная миниатюра, без полного декодирования.
- **FR-9.2.** Особый тип группы — **«Одно фото в разных форматах»**:
  - перцептивный хэш почти совпадает;
  - одинаковое разрешение с учётом поворота;
  - одинаковая дата съёмки, если она есть.

  Для таких групп правило автовыбора — «оставить формат X», по умолчанию JPEG.
- **FR-9.3.** Обычные «похожие» группы (серии, пересжатые копии) показываются отдельно от точных и **не отмечаются автоматически**.

### 5.4 Просмотр и выбор

- **FR-10.1.** Группы выводятся списком: превью, путь, размер, дата, разрешение. Сортировка по освобождаемому месту.
- **FR-10.2.** Можно сравнить два файла бок о бок (для фото — с синхронным зумом).
- **FR-10.3. Правило автовыбора «оставить»:**
  - самый старый (по умолчанию);
  - самый новый;
  - наибольшее разрешение или размер;
  - самый короткий путь;
  - файл из приоритетной папки (папки упорядочиваются);
  - заданный формат (FR-9.2).

  Отметки можно поправить вручную.
- **FR-10.4. Защита:** в каждой группе хотя бы один файл остаётся неотмеченным. Это проверяется на стороне ядра, а не только в интерфейсе.
- **FR-10.5.** Внизу показывается сводка: «Будет удалено N файлов, освободится X ГБ».
- **FR-10.6. Клавиатура:**
  - `Space` — предпросмотр;
  - `Del` — отметить или снять отметку;
  - `↑/↓` — переход по файлам;
  - `Ctrl+↑/↓` — переход по группам.

### 5.5 Действия

- **FR-11.1.** «В корзину» (по умолчанию) / «Переместить в папку» / «Удалить навсегда» (с подтверждением). Если корзина недоступна — как в FR-5.4.
- **FR-11.2.** Перед удалением ядро проверяет, что файл не изменился с момента сканирования (размер и mtime совпадают). Для точных дубликатов дополнительно проверяется, что оставляемый файл группы ещё существует.
- **FR-11.3.** Файлы только для чтения или занятые другим процессом не удаляются. По ним выводится понятная ошибка, остальные действия продолжаются.
- **FR-11.4.** Отчёт по группам и действиям можно экспортировать в CSV.

## 6. Уровень нагрузки на железо

### 6.1 Поведение

- **FR-12.1.** Переключатель уровня нагрузки находится в шапке окна. Он общий для конвертации и поиска дубликатов и **меняется на лету**, без перезапуска задач.
- **FR-12.2.** Уровни (N — число логических ядер; R = max(1, ⌈0.15·N⌉) — резерв для системы):

| Уровень | Бюджет потоков CPU | Приоритет процессов | HW-сессий видео | Назначение |
|---|---|---|---|---|
| **Авто** (по умолчанию) | динамически от 1 до max(1, N − R) (6.2) | ниже обычного | по 6.2 | компьютер остаётся отзывчивым |
| Низкий | max(1, ⌈N/4⌉) | низкий + низкий приоритет I/O + режим энергоэффективности | 1 | фоновая работа |
| Средний | max(1, ⌈N/2⌉) | ниже обычного | 1 | |
| Высокий | max(1, ⌈3N/4⌉) | обычный | 2 | |
| Максимум | N | обычный | предел из детекта | компьютер свободен |
| Свой | ползунок 1…N | выбирается | выбирается | |

- **FR-12.3. Приоритет процессов.**

  | Приоритет из таблицы | Windows | Linux |
  |---|---|---|
  | низкий | `IDLE_PRIORITY_CLASS` + `PROCESS_MODE_BACKGROUND_BEGIN` + EcoQoS (`PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, Windows 11) | `nice` 19 + `ioprio` класса idle |
  | ниже обычного | `BELOW_NORMAL_PRIORITY_CLASS` | `nice` 10 |

  Приоритет применяется к рабочим потокам ядра и ко всем дочерним ffmpeg, в том числе к уже запущенным. Поток интерфейса и WebView остаются с обычным приоритетом, чтобы окно отзывалось.

  Ограничения платформы:
  - На Linux без `CAP_SYS_NICE` приоритет можно только понизить. При переходе, например, с «Низкого» на «Максимум» уже запущенные задачи остаются с низким приоритетом, новый действует для новых задач.
  - Системные демоны вроде ananicy-cpp (по умолчанию в CachyOS) переопределяют приоритет процессов `ffmpeg` по своим правилам. Приложение с этим не борется; бюджет потоков при этом соблюдается.
- **FR-12.4.** Рядом с переключателем показывается фактическое состояние, например «Авто · 6 из 8 потоков · внешняя нагрузка 23 %». При наведении появляется мини-график за последние 60 с.
- **FR-12.5. Работа от батареи.** Уровень ограничен «Средним». Это отключается в настройках. Питание определяется так:
  - Windows: `GetSystemPowerStatus`;
  - Linux: `/sys/class/power_supply`.

### 6.2 Алгоритм «Авто»

1. Каждую секунду (через крейт `sysinfo`) замеряются:
   - общая загрузка CPU;
   - загрузка собственного дерева процессов: ядро и все дочерние ffmpeg по отслеживаемым PID;
   - свободная RAM;
   - источник питания.

   Загрузка процесса нормализуется к доле всей машины (0…1). `sysinfo` отдаёт её в процентах одного ядра, поэтому значение делится на N.
2. **Внешняя нагрузка:** E = clamp(общая − собственная, 0, 1), сглаженная EMA с α = 0.3.
3. **Целевой бюджет:** B = clamp(⌊N·(1 − E)⌋ − R, 1, max(1, N − R)).
4. **Гистерезис:**
   - уменьшение — сразу до B, если B ниже текущего бюджета 2 замера подряд;
   - увеличение — не более чем на max(1, ⌈N/8⌉) за шаг и только если B выше текущего 5 замеров подряд.
5. **Память:** если свободной RAM меньше 15 % или меньше 1.5 ГБ, новые задачи не запускаются, пока память не освободится. Для фото память оценивается как ширина × высота × 4 × 2 байт; для 24 Мп это около 200 МБ.
6. **HW-сессии:** одна, если E > 0.5, иначе до двух. Не больше предела, найденного при детекте.
7. **Применение бюджета:**
   - новый бюджет действует на **новые** задачи; запущенные досчитываются со своим числом потоков;
   - пока занятость выше бюджета, планировщик новые задачи не запускает;
   - снижение приоритета (FR-12.3) действует на запущенные задачи сразу.

### 6.3 Распределение бюджета (планировщик)

- Планировщик держит пул «токенов потоков» размером с текущий бюджет. Каждая задача берёт токены на старте и возвращает по окончании:

| Тип задачи | Токенов | Параметры |
|---|---|---|
| Фото (декод + кодирование) | 1–4 | max(1, min(4, ⌊бюджет / фото в очереди⌋)): на больших пачках по потоку на фото, на малых свободные потоки уходят на декодирование тайлов HEIC; число потоков libheif и WebP равно числу токенов |
| Видео, перепаковка | 1 | ограничено дисковым I/O |
| Видео, HW-кодирование | 1 + слот HW-сессии | при CPU-фильтрах (тональная компрессия на CPU, масштаб) — как CPU-кодирование |
| Видео, CPU-кодирование | t = clamp(бюджет, 1, 8) | `-threads t` для декодера и кодировщика, `-filter_threads t`; одновременно max(1, ⌊бюджет / t⌋) задач |
| Хэширование | 1 | дополнительно ≤ 4 читателя на SSD и 1 на HDD на каждый физический диск |

- Тип диска определяется так:
  - Linux: `/sys/block/*/queue/rotational`;
  - Windows: `IOCTL_STORAGE_QUERY_PROPERTY` (`IncursSeekPenalty`).

  Если определить не удалось, диск считается HDD.
- Фото и видео выполняются вперемешку: CPU-кодирование видео не должно занимать весь бюджет, пока в очереди ждут фото. Как минимум ⌈бюджет/2⌉ токенов доступно фото, если они есть в очереди.
- Число потоков у ffmpeg приблизительное: x264 создаёт служебные потоки сверх `-threads`. Точность обеспечивается вместе с приоритетом процесса, жёсткой гарантии нет.

## 8. Нефункциональные требования

### 8.1 Производительность (на машине из 1.1)

| Метрика | Цель | Замер этапа 1 |
|---|---|---|
| HEIC 24 Мп → JPEG, на один поток | ≤ 0.5 с | **1.07 с — не выполнено**: одно декодирование HEVC-тайлов в libheif занимает 0.71 с на поток. Пропускная способность на 8 потоках — 16 фото за 3.7 с (≈ 0.23 с на фото) |
| HEIC 24 Мп → PNG «Быстро», на один поток | ≤ 1.5 с | 0.98 с |
| Перепаковка видео | ≥ 100× realtime (ограничено диском) | ≈ 330× |
| HW H.264 1080p SDR | ≥ 5× realtime | ≈ 10× (VAAPI, только GPU) |
| Хэширование | ≥ 90 % скорости последовательного чтения диска | не замерялось на больших объёмах |
| Отклик интерфейса во время работы на уровне «Максимум» | ≤ 100 мс | — (этап 2) |
| Холодный старт приложения | ≤ 1.5 с | CLI ≈ 0.1 с |

Замеры шумные: машина разработчика при фоновой нагрузке нагревается до 91 °C и сбрасывает частоту, разброс между прогонами достигает 2×. Цель по HEIC → JPEG нужно либо пересмотреть, либо добиваться декодером быстрее libde265.

### 8.2 Надёжность и безопасность данных

- Ни при каком сценарии (ошибка, отмена, падение, выключение питания) не теряются исходники и не остаются битые файлы под финальным именем (FR-4.3, FR-4.4, FR-5.2–5.4, FR-10.4, FR-11.2).
- Падение ffmpeg или декодера не роняет приложение. Декодирование фото выполняется с ограничением по размеру входа (защита от «бомб» с огромным разрешением).
- **Пути:**
  - Unicode в путях (кириллица, эмодзи) поддерживается. Аргументы ffmpeg на Windows передаются в UTF-16, это делает `std::process::Command`.
  - На Windows поддерживаются длинные пути (> 260 символов) и сетевые диски (UNC). На этапе 1 нужно проверить, принимает ли встроенный ffmpeg такие пути. Если нет, ядро работает через временную жёсткую ссылку или копию с коротким путём.
- Приложение не обращается к сети и не собирает телеметрию.

### 8.3 Поставка

- **Windows:**
  - установщик NSIS ставит WebView2 Runtime, если его нет;
  - portable-zip требует уже установленного WebView2, на Windows 11 он есть всегда; при запуске без него показывается понятное сообщение.
- **Linux:**
  - AppImage со встроенным ffmpeg;
  - `.deb` с зависимостью от системного `ffmpeg (>= 6.1)`.

  Нужен WebKitGTK 4.1 (зависимость Tauri).
- Размер без ffmpeg ≤ 20 МБ. ffmpeg (статическая сборка) поставляется отдельным файлом рядом с приложением. На этапе 3 нужно проверить, что встроенная Linux-сборка ffmpeg поддерживает VAAPI. Если нет, для HW-кодирования на Linux нужен системный ffmpeg (FR-13.3).

### 8.4 Лицензии

- **Приложение:** MIT.
- **ffmpeg** запускается как отдельная программа и не линкуется. Это позволяет поставлять GPL-сборку с x264/x265. Лицензия и ссылка на исходники прикладываются в окне «О программе» и в дистрибутиве.
- **libheif, libde265, dav1d.**
  - libheif и libde265 распространяются под LGPL, dav1d — под BSD.
  - На Windows они поставляются как DLL (динамическая линковка), на Linux берутся из системы (`.deb`) или кладутся в AppImage.
- AGPL-зависимости не используются.
- **Патенты.** H.264/HEVC/AAC покрыты патентными пулами. Для бесплатного open-source приложения это допустимый риск, решение — использовать системные или аппаратные кодеки и не продавать приложение. Если приложение станет коммерческим, вопрос нужно пересмотреть до релиза.

### 8.5 Понятность для пожилых пользователей без опыта работы с ПК

Требование приоритетнее плотности и красоты интерфейса. Каждый пункт проверяем.

- **Текст.** Основной текст — не меньше 16 px, подписи — не меньше 14 px. Контраст основного текста с фоном — не ниже 7:1, второстепенного — не ниже 4.5:1. Интерфейс следует системному масштабу; в настройках есть «Крупный текст».
- **Цели нажатия.** Кнопки и другие элементы, на которые нажимают, — не меньше 44 × 44 px, между ними не меньше 8 px. Главная кнопка экрана крупнее остальных и подписана словами, а не только значком.
- **Ничего скрытого.** Нет действий, доступных только наведением мыши, двойным щелчком, правой кнопкой, перетаскиванием или сочетанием клавиш: у каждого действия есть видимая кнопка с текстом. Важные пояснения написаны рядом с элементом, а не во всплывающей подсказке.
- **Простые слова.** В основном режиме нет терминов: кодек, HEVC, H.264, CRF, метаданные, EXIF, HDR, sRGB, поток, мегапиксели. Вместо них — что это значит для человека («открывается на любом телефоне», «файл станет меньше»). Термины допустимы только в «Расширенных настройках» и журнале.
- **Пошаговость.** Основной сценарий виден как последовательность: 1) выберите фото и видео, 2) выберите, что с ними сделать, 3) нажмите «Начать». На экране одно главное действие; лишние элементы появляются, только когда нужны.
- **Безопасность по умолчанию.** Безвозвратное удаление недоступно в основном режиме. Перед необратимым действием — подтверждение простыми словами, где безопасный вариант выбран по умолчанию и стоит первым. Отмена всегда на виду.
- **Понятный результат.** Итог — фраза вроде «Готово: 30 фото сохранены в папку «Фото с телефона»» и крупная кнопка «Открыть папку». Ошибка объясняет, что случилось и что сделать, без кодов и вывода ffmpeg — подробности только в журнале.
- **Прогресс человеческим языком.** «Сделано 12 из 30, осталось примерно 2 минуты», без процентов скорости и долей.
- **Проверка.** Перед релизом пожилой человек без опыта работы с ПК без подсказок выполняет сценарии 1 и 2 из раздела 3. Каждое место, где он остановился или ошибся, — дефект.

## 9. Архитектура

```
converter/
├─ crates/core/            # библиотека без UI
│  ├─ scan                 # обход, определение типа, Live Photo, облачные файлы
│  ├─ probe                # ffprobe, метаданные фото, HDR-признаки
│  ├─ plan                 # выбор операции: remux / HW / CPU; резервирование имён
│  ├─ scheduler            # очередь, пул токенов, пауза/отмена
│  ├─ governor             # уровень нагрузки, алгоритм «Авто», приоритеты, батарея
│  ├─ video                # запуск ffmpeg, парсинг -progress, детект HW, тональная компрессия
│  ├─ image                # libheif + кодировщики PNG/JPEG/WebP, EXIF/ICC/ориентация
│  ├─ dupes                # размер → частичный → BLAKE3, phash, кэш
│  └─ fs_ops               # атомарная запись, журнал временных файлов, корзина, проверки
├─ crates/cli/             # clap + indicatif
└─ app/
   ├─ src-tauri/           # команды Tauri → core, события прогресса, single-instance
   └─ src/                 # React + TS
```

- Ядро сообщает о событиях через канал: `JobQueued`, `JobProgress`, `JobFinished`, `GovernorTick`, `DupesProgress`, `DupesGroup`. Tauri пересылает их во фронтенд с частотой не выше 10 событий в секунду на задачу; события агрегируются пачками.
- Фронтенд: Tailwind + shadcn/ui, состояние в zustand, таблицы через TanStack Virtual.
- Миниатюры генерирует ядро. Они кэшируются на диске и отдаются через собственный протокол Tauri (`asset:`/custom scheme), а не base64 в событиях.

## 12. Тестирование

- **Unit-тесты:**
  - планировщик токенов;
  - алгоритм «Авто» на синтетических рядах нагрузки (резкий скачок, пила, полная загрузка, N = 1);
  - резервирование и конфликты имён;
  - таблица профилей качества;
  - правила автовыбора дубликатов;
  - инвариант «в группе остаётся хотя бы один файл».
- **Интеграционные тесты на файлах из `data_media/` и наборе эталонов:**
  - результат открывается ffprobe;
  - длительность совпадает;
  - ориентация применена, а EXIF Orientation = 1;
  - ICC-профиль на месте;
  - HDR-видео после «Совместимо» имеет `color_transfer=bt709`;
  - отмена в середине кодирования не оставляет временных файлов и не трогает исходник.

  Эталоны: HDR-видео iPhone, вертикальное видео, переменная частота кадров, HEIC с поворотом, Live Photo, файл с дорожкой `mebx`.
- **Тесты безопасности данных:**
  - имитация падения ffmpeg и самого приложения;
  - нехватка места на диске;
  - изменение файла между сканированием и удалением;
  - недоступная корзина.

  Во всех случаях исходники целы.
- **CI:** GitHub Actions, сборка и тесты под `windows-latest` и `ubuntu-latest`. HW-кодирование в CI не проверяется (нет GPU), проверяется вручную по чек-листу перед релизом.

### Этап 2 (GUI)

Приложение Tauri 2 + React (`app/`) реализовано и проверено на Linux сквозным прогоном через окно (отладочная сборка выполняет JS по `--dev-eval`) и запуском релизной сборки: бинарник 15.5 МБ.

**Сделано:**
- вкладки «Конвертация», «Дубликаты», «Журнал», окно настроек;
- добавление файлов кнопками, перетаскиванием и аргументами запуска; одиночный экземпляр передаёт пути в открытое окно;
- виртуализированный список с миниатюрами, разрешением, длительностью, HDR и Live Photo; фильтр и поиск;
- прогресс по файлам и общий, оставшееся время, пауза, отмена всего и одного файла, итог с «Повторить ошибочные» и «Найти дубликаты в папке результата»;
- предупреждение о нехватке места до старта (FR-4.6), пауза при нехватке во время работы;
- индикатор нагрузки из ячеек-потоков в шапке, уровни и «Свой» (FR-12.1, FR-12.4);
- дубликаты: группы с превью, правила «что оставить», защита последнего файла группы, корзина/перемещение/удаление с подтверждением, CSV, клавиатура (FR-10.6);
- настройки в `settings.toml`, пресеты, тема, источник ffmpeg, перепроверка видеокарты, очистка кэша миниатюр;
- запрет сна, уведомление по окончании, подтверждение закрытия во время работы (FR-6.6–6.8).

**Не сделано:**
- сравнение двух файлов бок о бок с синхронным зумом (FR-10.2) — есть только крупный предпросмотр выбранного;
- мини-график нагрузки за 60 с (FR-12.4);
- запоминание размера и положения окна (FR-13.5);
- пресеты удаляются только все сразу, без переименования.

**Не проверено:**
- сборка и запуск приложения на Windows (добавлено в CI);
- реальное перетаскивание мышью, уведомление и запрет сна — в среде разработки нет средств ввода; пути проверены через второй запуск.

**Особенность WebKitGTK:** `<img>` не грузит картинки из собственной схемы `thumb://` на странице другого источника, а `fetch` с CORS проходит. Поэтому миниатюры загружаются через `fetch` в blob-URL (`app/src/lib/thumbs.ts`).

### Этап 3 (поставка)

Сделано и проверено на Linux: `.deb` (6 МБ, системный ffmpeg ≥ 6.1) и AppImage (238 МБ, встроенные ffmpeg 8.1.3 и libheif). Встроенная Linux-сборка ffmpeg поддерживает VAAPI и QSV (вопрос раздела 8.3 закрыт). Окно «О программе» с лицензиями (раздел 8.4).

Отличия от раздела 8.3:
- libheif в Linux-выпусках вшивается статически (LGPL соблюдается: исходники приложения открыты, MIT) — так AppImage не зависит от плагинов libheif системы;
- `.deb` ставится на Ubuntu 24.04+ (ffmpeg ≥ 6.1); для Ubuntu 22.04 — AppImage;
- AVIF во выпускных Linux-сборках не поддерживается (libheif без dav1d).

Windows-сборка (NSIS, portable-zip) собирается в CI; выпуск 0.1.0 опубликован. Вживую на Windows не проверялась.

### Этап 4 (расширения)

**«Одно фото в разных форматах» (FR-9.2, сценарий 3)** — сделано в ядре, CLI и интерфейсе:
- кандидаты — фото одного размера в пикселях с учётом поворота и одной даты съёмки (оба читаются из заголовка, без декодирования); отпечаток (64-битный dHash по уменьшенной картинке, для HEIC — по встроенной миниатюре) считается только у файлов, у которых есть возможная пара другого формата;
- одно фото — разные форматы и расстояние Хэмминга ≤ 6; файл без даты присоединяется только к одному, самому похожему, иначе он склеил бы соседние кадры серии;
- файлы из групп точных копий в поиск форматов не берутся (иначе файл попал бы в две группы); пара найдётся после уборки копий;
- правило — «оставить формат X», по умолчанию JPEG; нет такого формата — остаётся самый большой файл;
- в простом режиме пары убираются отдельной кнопкой «Оставить только JPEG», а не вместе с точными копиями; в CLI — только с `--formats`.

**Похожие фото (FR-9.1, FR-9.3)** — сделано в ядре, CLI и интерфейсе:
- по умолчанию выключено; отпечаток каждого фото — по встроенной миниатюре (HEIC — из контейнера, JPEG — из EXIF, если её пропорции совпадают со снимком), иначе по полному декодированию; отпечатки кэшируются в `hashes.json`, повторный поиск их не пересчитывает. 40 JPEG по 12 Мп с миниатюрами — 0,09 с, без них — 1,5 с;
- строгость — выбор из четырёх («Не искать», «Почти одинаковые» ≤ 5 бит, «Похожие» ≤ 9, «С большим допуском» ≤ 13) вместо ползунка «Строго ↔ Мягко»: ползунок без делений непонятен главному пользователю (раздел 8.5);
- фото присоединяется к первой группе, чей первый снимок отличается не больше порога и имеет те же пропорции (±2 %); сравнение с первым, а не с любым, не даёт длинной серии «перетечь» в другие кадры;
- в похожие не берутся файлы из групп точных копий и одного фото в разных форматах;
- группы не отмечаются автоматически ни в интерфейсе, ни в CLI; в простом режиме — отдельный абзац и кнопка «Посмотреть похожие фото».

Отличие от FR-9.1: отпечаток свой (64-битный dHash), без крейта `image_hasher`.
