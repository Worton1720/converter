# Набранный опыт

Проблемы, на которые уже потрачено время, — с причиной и решением. Прежде чем чинить что-то странное, поищите здесь; наткнулись на новое — допишите запись в нужный раздел.

Формат записи: **что видно** → почему → что сделано (и где в коде).

## Видео и ffmpeg

- **HEVC из libx265 выходит с неверными цветами (HDR-метки, блёклая картинка).** libx265 игнорирует выходные `-color_trc`, `-color_primaries`, `-colorspace`. Цвет задаётся самим кадрам фильтром `setparams` — см. `video::build_args`.
- **MOV принимался за MP4 и «перепаковывался» впустую (или наоборот).** У MOV и MP4 одинаковый `format_name` в ffprobe (`mov,mp4,m4a,…`). Различать по тегу `major_brand` (`qt` — MOV), см. `is_noop`.
- **Видео с iPhone не перепаковывалось в MP4.** В MOV с iPhone есть дорожки данных `mebx` (метаданные) и звук APAC, которых MP4 не принимает. Дорожки `mebx` отбрасываются, APAC пропускается при выборе аудио.
- **Ctrl+C в консоли убивал ffmpeg раньше, чем мы успевали убрать временный файл.** Сигнал уходит всей группе процессов терминала. ffmpeg запускается в своей группе (`setpgid` в `pre_exec`) плюс `PR_SET_PDEATHSIG`, чтобы он не пережил приложение — `sys.rs`.
- **Приоритет ffmpeg «не применяется» (nice 9 вместо нашего).** На машине разработчика ananicy-cpp по правилу `ffmpeg → Heavy_CPU` переписывает nice/ioprio. Это не баг: проверять приоритет на потоках самого converter (`ps -L`), а не на ffmpeg.
- **Сборки ffmpeg от BtbN со временем исчезают.** Датированные `autobuild-*` удаляются. Выпуск и контрольные суммы зафиксированы в `tools/fetch-ffmpeg.sh`; когда ссылка умрёт — обновить TAG/BUILD/SHA (зеркало пока не сделано, см. `tasks.md`).
- **`.deb` не ставится на Ubuntu 22.04.** Там ffmpeg 4.4, а нужен ≥ 6.1. Для 22.04 — AppImage со встроенным ffmpeg.

## Фото и libheif

- **AppImage не открывает HEIC на Ubuntu 24.04+.** Там декодер HEVC вынесен в отдельный плагин libheif, и AppImage его не захватывает. Выпускные Linux-сборки идут с фичей `embedded-libheif` (libheif статически, libde265 встроенный декодер, без плагинов). Заодно это сняло проблему старой libheif 1.12 на Ubuntu 22.04.
- **libheif на Windows не открывает файлы с русскими буквами в пути.** Она работает с ANSI-путями. HEIC читается в память и открывается `read_from_bytes` (`photo/decode.rs`).
- **В Windows-поставку попала `libx265.dll` (GPL).** Порт libheif в vcpkg по умолчанию включает фичу `hevc` — кодировщик x265. Нам нужно только чтение: ставить `libheif[core,libde265]` (в старых портах, где libde265 не фича, — `libheif[core]`). CI падает, если `libx265.dll` окажется в поставке.
- **HEIC → JPEG медленнее цели ТЗ (≈0,9 с на поток вместо 0,5 с).** Исследовано: декодирование HEVC 24 Мп — 0,61 с на поток в libheif; ffmpeg «быстрее» по часам (0,22 с) только потому, что каждый из 45 тайлов декодирует в своём потоке даже с `-threads 1` — по процессорному времени (0,84 с) то же самое. Сравнивать декодеры по `user`-времени, не по часам. Остаток — кодирование JPEG 0,24 с в одном потоке. Цель пересмотрена (ТЗ 8.1). Затем кодирование JPEG перевели на libjpeg-turbo: замер A/B на 50 фото (чередуя варианты из-за перегрева) — пачка −15 %, одно фото 0,65 → 0,47 с, PSNR и размер те же. Ловушка: без nasm libjpeg-turbo тихо собирается без SIMD и не быстрее прежнего — включён `require-simd`, сборка без nasm падает.

- **В CI (Ubuntu 24.04) HEIC не открывался: «Unsupported codec».** Системная libheif загружает декодер HEVC плагином из отдельного пакета `libheif-plugin-libde265`; без него открываются только PNG/JPEG. Поймано автотестом интерфейса. Выпускные Linux-сборки не затронуты — в них libheif вшита со встроенным libde265. Тем, кто собирает программу с системной libheif, нужен этот пакет.

## Поиск одинаковых файлов

- **Жёсткие ссылки считались лишними копиями, и «освободится» показывало неправду.** Это одно содержимое на диске. Ссылки схлопываются в представителя (`FileEntry.links`); при удалении убираются все имена, место считается один раз.
- **Лишнее чтение при частичном хеше.** Был холостой `read` перед чтением хвоста — убран из `partial_hash`.
- **Одно фото в разных форматах: файл без даты склеивал разные кадры.** PNG без метаданных «совпадал» и с HEIC за 10:00:00, и с соседним кадром серии за 10:00:01 — через него два разных снимка попадали в одну группу. Файлы с датой связываются только с той же датой, файл без даты — только с одним, самым похожим (`cluster_same_photos`). Поймано модульным тестом `same_photos_need_matching_dates`.
- **Отпечатки для всей фототеки были бы слишком дорогими.** У iPhone тысячи снимков одного размера 4032×3024, а JPEG декодируется целиком. Дата съёмки читается вместе с размером из заголовка, и отпечаток считается только у файлов с возможной парой другого формата.
- **Кэш хэшей мог вернуть устаревший полный хэш (было и в 0.1.0).** `store` обновлял размер и время записи, но оставлял старые хэши. Файл переписали тем же размером → частичный хэш пересчитан и сохранён → запись «совпадает» по времени → прежний полный хэш выглядит действительным, и файл мог попасть в чужую группу «одинаковых». Теперь `HashCache::entry` сбрасывает все хэши, если изменились размер, время или file ID; тест `cache_forgets_hashes_of_changed_file`. Нашлось при добавлении отпечатков фото в тот же кэш — у фото `file_id` сначала не заполнялся, и записи переписывались туда-обратно.
- **Похожие фото «перетекали» по длинной серии.** При связывании любых близких пар цепочка A~B~C~… собирает в одну группу кадры, которые между собой уже не похожи. Фото сравнивается с первым снимком группы (`cluster_similar`), а не с любым.
- **Группы форматов и `DupGroup.size`.** У точных копий размер у всех файлов один, у одного фото в разных форматах — разный. Освобождаемое место считать по размеру каждого отмеченного файла (интерфейс, CLI, CSV), иначе сумма врёт.

## Перенос с телефона

- **Android на KDE не становится папкой.** kio-fuse отвечает «does not support mounting of URLs with a scheme of mtp» (iPhone, `afc:/`, монтирует). Для Android — `kioclient`: `ls` (только имена), `stat` (размер, дата, тип), `copy` (дата изменения сохраняется). Запуск `kioclient` стоит ~0,3 с, поэтому `stat` идёт по 8 параллельно (≈22 мс на файл); копирование ~18 МБ/с. Проверено на Redmi Note 14 Pro: 63 файла, 417 МБ за 23 с.
- **В выпуске 0.5.0 (AppImage) телефон Android не находился, хотя `converter phone` из консоли его видел.** AppImage выставляет `LD_LIBRARY_PATH`, `QT_PLUGIN_PATH`, `PATH` внутрь образа, и дочерний системный `kioclient` грузил библиотеки образа: `liblzma.so.5: version XZ_5.4 not found (required by /usr/lib/libKF6Archive.so.6)` — без вывода, программа видела «устройств нет». Все запуски программ системы (kioclient, busctl, gdbus, ffmpeg/ffprobe) идут через `sys::host_command`: при заданном `APPDIR` части путей внутрь образа убираются. Проверять под AppImage: подключить образ `--appimage-mount`, задать его переменные (`APPDIR`, `LD_LIBRARY_PATH`, `PATH`…) и запускать тестовую программу через `/lib64/ld-linux-x86-64.so.2 --library-path /usr/lib` — иначе она сама споткнётся о библиотеки образа. И в zsh массив переменных для `env -i` — только через bash: `$E` в zsh не разбивается на слова.
- **«Программа видит не все фото с Android»: искали только в `DCIM`.** На Redmi в `DCIM` 63 снимка (ещё 60 — корзина `.trashed-…`), а галерея телефона показывает ~360: Telegram и ВК кладут в `Pictures/…` и `Movies/…`, загрузчики — в `Download/…`, WhatsApp (Android 11+) — в `Android/media/com.whatsapp/WhatsApp/Media/…`. Теперь у Android просматривается весь накопитель по правилам галереи: без скрытых папок, без папок с `.nomedia` (у WhatsApp при выключенной «Видимости медиа» это `Private` и `Sent`, у AyuGram — кэш вложений на 23 тысячи файлов), без `Android/*` кроме `media` и без наклеек. У iPhone и карт — по-прежнему `DCIM`.
- **`kioclient ls` не отличает папки от файлов, а у папок бывают точки в имени** (`com.whatsapp`): фильтр «без расширения — папка» в них не заходил. Сведения запрашиваются и у имён, у которых «расширение» не похоже на файловое (длиннее 4 знаков или не из букв и цифр).
- **Список большой папки по MTP — десятки секунд** (23 тысячи файлов — 35 с), и телефон отвечает по очереди: больше 8 параллельных `kioclient` не быстрее. Перед чтением папки — `stat <папка>/.nomedia` (1–2 с): скрытую не читать. Обход — общей очередью задач, а не по уровням, чтобы долгий список не держал остальное. Весь накопитель Redmi: 29 с.
- **Ожидание `kioclient` опросом раз в 50 мс** добавляло в среднем 25 мс к каждому из сотен запусков. Конец вывода (труба закрылась) — знак, что программа завершается: дальше ждать без опроса (`run_watched`).
- **Повторный поиск — память, а не телефон.** Списки папок нужны каждый раз (что появилось и пропало), а сведения о файлах (размер, дата) и признак «папка скрыта» запоминаются в `phone-memory.json`: Redmi — 4 с вместо 35. О пройденном телефоне в память пишется только увиденное сейчас, о других — прежнее.
- **Копирование пачкой `kioclient copy a b … папка/`** экономит ~50 мс на файл (замер на 20 файлах: снимки экрана 1,6 → 0,6 с, фото камеры 3,6 → 2,6 с), а не 0,3 с, как ожидалось. Пачка — в одну папку месяца и с разными именами (файл получает имя, как на телефоне); KIO пишет в `.part`, поэтому при отмене целые файлы можно оставить. Проверять без телефона: `kioclient` понимает адреса `file://` — так устроен тест `copies_batches_through_kioclient`.
- **Первый поиск после простоя нашёл 169 файлов из 361 за 187 с** (повтор сразу — все за 35 с). Причина не поймана (к следующему замеру телефон отключили); вероятно, служба KDE заново открывала устройство под восемью одновременными запросами. Неудачный `ls`/`stat` теперь повторяется через 0,5 с, неудача и после этого считается (`unread`) и показывается — молча терять снимки нельзя.
- **`FILE_TYPE` в `kioclient stat` — восьмеричный st_mode с ведущим нулём:** `0040000` у папки, `0100000` у файла. Сравнение со строкой `040000` дало «ни одной папки» — разбирать как число и маской `0o170000`.
- **Корзина Android — скрытые `.trashed-…` рядом со снимками,** в `DCIM/Camera` их было больше трети. Скрытое не переносится; при ручной сверке числа файлов их не считать.
- **Даты в выводе `kioclient`** — `Sun Oct 18 15:15:22 2026`; язык закреплён `LC_TIME=C.UTF-8`, разбор на всякий случай понимает и русские сокращения.

## Интерфейс (Tauri, WebKitGTK)

- **Миниатюры не грузятся на Linux.** WebKitGTK не показывает `<img src="thumb://…">` со страницы другого источника, а `fetch` с CORS проходит. Миниатюры идут через `lib/thumbs.ts` (fetch → blob-URL), ответы протокола содержат `Access-Control-Allow-Origin`.
- **Правка CSP «ничего не меняет».** В dev-режиме Tauri CSP не применяет. Проверять CSP только релизной сборкой.
- **`--dev-eval` падает со «Script error».** Повторный запуск того же кода переобъявляет глобальные `const`. Оборачивать код в асинхронную IIFE `(async () => { … })()`.
- **После перезапуска `tauri dev` команды `--dev-eval` уходят «в никуда».** Если старый экземпляр не закрылся, новый процесс становится основным в single-instance. Сначала убить лишние `converter-app` (по `pgrep -x`), потом запускать.
- **Radix Select падает на пустом значении.** Пустая строка у него зарезервирована. Использовать значение-заглушку `"none"`.
- **Поиск кнопки «Расширенные» по `aria-expanded` находил выпадающие списки.** Radix Select тоже ставит этот атрибут. Искать элемент по тексту.

## Значки

- **Одного `.ico` для всех систем мало.** На Linux Tauri берёт значок окна и значки `.deb`/AppImage только из PNG. Минимум — `icon.ico` и `icon.png` 512 px; `tauri icon` не использовать, он раскладывает десяток файлов. Сборка — `tools/icon/make-icon.sh`.
- **ImageMagick делает `.ico` на 370 КБ.** Он пишет кадры в BMP. Скрипт склеивает PNG-кадры сам (как крейт `ico` у Tauri) — 31 КБ.
- **На скриншоте полосы в градиентах.** PNG8 (256 цветов). Скриншоты для README — в WebP.

## Git и репозиторий

- **`app/src/lib/` не попадала в коммит.** `.gitignore` остался от Python-шаблона, а в нём `lib/`. Файл переписан под Rust/Tauri; после правки `.gitignore` смотреть `git status --ignored`.
- **`app/src-tauri/icons/` не попадала в коммит.** Глобальный `~/.config/git/ignore` содержит правило macOS `Icon?`. В проектном `.gitignore` папка возвращена явно (`!app/src-tauri/icons/`).
- **После переписывания `.gitignore` в индекс попал `.env`.** Он был исключён старым шаблоном. Перед коммитом просматривать список добавляемых файлов.
- **В CI `tools/build-linux.sh: Permission denied`, а хук перед коммитом в свежем клоне молча не работает.** При `core.fileMode=false` бит `+x` не записывается в git, а git пропускает неисполняемые хуки. Ставить права явно: `git update-index --chmod=+x <файл>`. Повторилось с новым `tools/smoke-test.sh` — правило «помнить» не работает. Теперь: `core.fileMode=true` в этом клоне (лишний `+x` у `.gitignore`, `README.md`, `tasks.md` снят — он и мешал включить), а хук перед коммитом отказывает, если какой-то `*.sh` или файл в `.githooks/` записан в git без `100755`.
- **Личные файлы в образцах.** В `data_media/` лежат семейные фото — в репозиторий она не входит, скриншоты для README делаются на сгенерированных образцах.

## CI и выпуск (GitHub Actions)

- **Windows-сборка падает на clippy, хотя локально всё зелёное.** Код под `cfg(windows)` локально не компилируется (нет Windows-таргета). Новые замечания видны только в CI — писать такой код особенно аккуратно (вложенные `if let` сразу через `&&`, переменные теста — используемые на обеих системах).
- **`converter-app` не собирается на Windows: `glob pattern resources/windows-dlls/* … didn't match`.** `tauri.windows.conf.json` подмешивается в любую сборку, включая clippy и тесты, и требует файлы из `bundle.resources`. CI копирует DLL из vcpkg, вместо ffmpeg кладёт заглушку.
- **`vcpkg install` занимает ~10 минут на каждый прогон.** Кэш `C:\vcpkg\installed` через `actions/cache`, ключ — версия порта libheif и набор фич.
- **`libheif has no feature named libde265` — но только на части прогонов.** Образы GitHub приходят с vcpkg разной свежести. Набор фич выбирается по `C:\vcpkg\ports\libheif\vcpkg.json`.
- **После смены фич libheif линковщик ищет `libx265.lib`.** `Swatinem/rust-cache` вернул старый вывод сборочного скрипта `libheif-sys`. Сменить `key` у rust-cache при любой смене состава vcpkg.
- **Предупреждение «Node.js 20 is deprecated».** `actions/checkout` и `actions/setup-node` обновлены до v5; `actions/cache@v4` и `pnpm/action-setup@v4` пока на Node 20 — только предупреждение.
- **Статус задания в `gh run view` «in_progress», хотя прогон завершён.** Задержка API GitHub — смотреть общий `status`/`conclusion` прогона.
- **«Выпуск на GitHub не появился».** Ручной запуск workflow только собирает пакеты, а публикация тогда была по тегу — тега не было. Сейчас выпуск создаётся слиянием dev → master, если версии из `Cargo.toml` ещё нет среди тегов; иначе в прогоне notice «версия уже выпущена».
- **`tools/release.sh` падал на первом выпуске.** Версия в файлах уже совпадала с выпускаемой, и `git commit` завершался «nothing to commit». Коммит делается только при изменениях (`git diff --cached --quiet ||`).
- **Имена обязательных проверок в защите master.** В запросе на слияние задания CI называются `linux` и `windows`, а внутри release.yml (через `workflow_call`) — `tests / linux`. Защита ссылается на имена из запроса.
- **Каждая проверка в запросе dev → master видна дважды.** CI запускается и на push в dev, и на сам запрос. Безвредно; обязательные проверки берут любую.
- **Чистка истории после выпуска.** Тег `v0.1.0` должен указывать ровно на код, из которого собраны файлы выпуска. При переписывании истории тег переносится принудительным push (`git push -f origin v0.1.0`) — выпуск привязан к имени тега и не теряется; если тег удалить, выпуск станет черновиком. Защита master запрещает force-push — на время снять `allow_force_pushes` и вернуть. Перед переписыванием — `git bundle create … --all`. Push тега запускает workflow **из коммита под тегом**, то есть старые: перенос `v0.1.0` поднял старые CI и Release (тот упал бы на повторном создании выпуска). Сразу после push тега — `gh run cancel` и удалить прогоны (удалять можно только завершённые, иначе HTTP 403).

- **Автообновление: «The update was signed for version 0.2.0 but the update endpoint announced version 9.9.9».** Подпись Tauri содержит версию — подменить её в `latest.json` нельзя (это защита). Проверка установки: собрать ту же программу с `--config '{"version":"0.1.9","plugins":{"updater":{"endpoints":["http://127.0.0.1:8765/latest.json"],"dangerousInsecureTransportProtocol":true}}}'` и раздать настоящую подписанную 0.2.0 с локального сервера. Так проверено на AppImage: скачала, проверила подпись, заменила файл, перезапустилась.
- **Ошибки обновления не попадали в файл журнала** — только во вкладку «Подробности», и по журналу было не понять, что случилось. `update.rs` пишет ошибки проверки и установки в `converter.log`.
- **Запрос dev → master не сливался: «the base branch policy prohibits the merge».** Linux-задание в прогоне для push в dev зависло на 40 минут; обязательная проверка `linux` числилась незавершённой, хотя в прогоне для самого запроса она прошла. Отменить зависший прогон, дождаться отмены, `gh run rerun <id> --failed`, затем слить. Фоновое ожидание «все проверки не pending» на зависшем задании не заканчивается — ставить ему предел времени. Повторилось несколько раз: задание висело на шаге «Системные зависимости» (`apt-get` на машине GitHub). У шага apt предел, у каждого задания — 90 минут. Сбои повторялись почти каждый день, поэтому установка идёт через `tools/apt-install.sh`: три попытки, у каждой свой предел, у apt — таймауты и повторы загрузки. Не помогло 23.10: зеркало azure.archive.ubuntu.com отдавало ~20 КБ/с, 159 МБ не успевали за попытку, а повтор шёл к тому же зеркалу. Теперь скачанные .deb лежат в `~/apt-archives` (кэш GitHub между прогонами, при повторе не качаются заново), а после первой неудачи — переход на archive.ubuntu.com. Позже выяснилось, что застревает само зеркало `azure.archive.ubuntu.com` (на пакете WebKit), и три попытки к нему же не помогают — вторая и третья попытки идут через `archive.ubuntu.com` и `mirrors.edge.kernel.org`. Подвох: на машинах GitHub источники указывают на список зеркал `/etc/apt/apt-mirrors.txt` (`mirror+file:`), а не на адрес в `ubuntu.sources` — первая версия правила не тот файл, и все попытки снова шли к azure. Уже скачанные пакеты остаются в `~/apt-archives`, следующая попытка докачивает остальное.

- **Автотест нажал не ту кнопку.** После `setTab("dupes")` экран меняется не сразу, и поиск по тексту «Найти одинаковые файлы» нашёл кнопку «…в этой папке» на прежнем экране. В сценариях ждать признак нового экрана (`until(() => text().includes(...))`) и только потом нажимать.
- **Автотест: щелчок сразу после рамки выделения не срабатывал.** После протягивания рамки `useMarquee` гасит ближайший щелчок (отпускание кнопки не должно переключить снимок) и снимает перехват на следующем такте. Тест нажимал кнопку в тех же микрозадачах — до снятия перехвата. В тестах после рамки — пауза; у человека щелчок не бывает так быстро.
- **Автотест ходил в сеть за обновлением.** Свежие настройки включают проверку обновлений; `tools/ui-test.sh` пишет `check_updates = false` в тестовый `settings.toml`. Заодно: в режиме разработки React запускает эффекты дважды — проверка при запуске защищена флагом.

## Замеры и машина разработчика

- **Ложная «регрессия» в бенчмарках.** Ноутбук (Comet Lake-U) греется до ~91 °C, разброс между прогонами до 2×. Сравнивать варианты только A/B в одном процессе с чередованием.
- **Нет `bc` и `/usr/bin/time`, шелл агента — zsh.** Время — `ffmpeg -benchmark` или `date +%s%N`; команды со списками аргументов — через `bash -c` (zsh не разбивает `$args` на слова).
- **`pkill -f <строка>` убил собственный шелл (код 144).** Строка есть и в его командной строке. Убивать по `pgrep -x <имя>`.
- **Без TTY индикатор прогресса CLI ничего не выводит.** indicatif прячет вывод, если stderr не терминал. Сообщения идут через `say()`.

- **Вложенный сеанс для тестов ломал службу специальных возможностей пользователя.** Даже со своей шиной D-Bus службы вложенного сеанса (at-spi-bus-launcher) пишут сокеты в общий `XDG_RUNTIME_DIR` (`/run/user/<uid>/at-spi/bus_0`) поверх настоящих; после выхода сокет пропадал — подключение отклонялось, программы запускались с задержкой, ожидая AT-SPI. Лечение: `systemctl --user restart at-spi-dbus-bus.service`. Профилактика: у вложенного сеанса своя папка `XDG_RUNTIME_DIR` и `NO_AT_BRIDGE=1` (`tools/ui-test.sh`). Вложенный сеанс нельзя использовать и для нажатия кнопок через AT-SPI: регистратору нужен systemd.
- **`rm -rf target/ui-test`: «Каталог не пуст».** kwalletd прошлого вложенного сеанса ещё дописывал в тестовую папку — очистка повторяется после паузы.

## Снимки экрана и работа на машине пользователя

- **Скриншот «окна программы» оказался браузером, мессенджером, файловым менеджером пользователя.** Пользователь работает за той же машиной с несколькими мониторами: `spectacle -a` снимает активное окно, `-m` — монитор под курсором, `keepAbove` не помогает. Так не снимать: каждый снимок сначала смотреть, чужое — сразу в корзину; для публичных скриншотов — просить пользователя или снимать конкретное окно.
- **В скриншоте видны служебные пути с именем пользователя.** Перед снимком подменять пути в DOM через `--dev-eval` или класть образцы в нейтральную папку.
- **Нажимать кнопки в собранной программе без средств ввода.** В выпускной сборке нет `--dev-eval`. Выручают специальные возможности: запуск с `GTK_MODULES=gail:atk-bridge NO_AT_BRIDGE=` (в сеансе выставлен `NO_AT_BRIDGE`, без сброса окно не видно в AT-SPI), затем Python `gi.repository.Atspi`: найти приложение `converter-app`, кнопку по имени и вызвать `get_action_iface().do_action(0)`. Текст из `div` без ролей так не прочитать — смотреть журнал `converter.log`.
- **После `tools/ui-test.sh` у пользователя перестали работать Alt+Tab и все сочетания KWin.** Невидимый `kwin_wayland --virtual` запускался в общей сессионной шине D-Bus: не сумев занять `org.kde.kglobalaccel` («Failed to register service»), он регистрировал свои действия в kglobalaccel настоящего KWin, а при выходе снимал их — компонент `kwin` становился неактивным (`qdbus6 org.kde.kglobalaccel /component/kwin …Component.isActive` → `false`). Решение: вложенный KWin — через `dbus-run-session`. Починка без перезахода: для каждого действия из `allShortcutInfos` компонента `kwin` вызвать `busctl --user call org.kde.kglobalaccel /kglobalaccel org.kde.KGlobalAccel setShortcut asaiu 4 kwin <действие> KWin <название> 0 2` (флаг SetPresent, сочетания сохраняются).
